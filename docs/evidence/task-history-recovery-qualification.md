# Historical task recovery qualification

Issue [#177](https://github.com/vypdev/domus/issues/177) corrects a misleading task-load warning after
recovering a creation whose effect was rolled away by restoration. The original historical receipt
remains visible; the Tasks controller refreshes the authorized current list without selecting a task
or material cycle from that receipt. Committed-result handling and genuine read failures retain their
existing behavior. No command is resent and no new request key is generated by recovery.

This is a witness for the existing `platform-restoration-C15` historical/current-state distinction,
under REST-06. It does not introduce a case identity or complete the restoration capability.

## Source verification

- `frontend/tests/task-controller.test.ts`: both previously committed and uncertain creations recover
  their original historical operation with the rolled-away task unavailable; current list failures
  remain visible, authorization denial retires private facts, and historical category/material
  results do not follow their former resources.
- `frontend/tests/e2e/tasks.spec.ts`: `historical creation recovery reads current tasks without probing
  rolled-away work` runs in native and standalone modes, in English with keyboard activation and
  Spanish at 390px with actual Playwright touch activation. A real fixture snapshot/restore removes
  a later creation while retaining its original receipt. The checkpoint task and its completion are
  unchanged, an independent new draft survives recovery, there is no load warning, no request for
  the rolled-away occurrence and no task write. Database counts remain unchanged.
- The original controller fails both creation regressions with `unavailable`; the corrected controller
  passes the complete frontend suite with all four supported coverage metrics at 100% globally and
  per file. Type checks and the production UI build are separate gates.

Browser fixtures supply fictional identity and operator controls only in test code. They do not
prove a real Home Assistant installation, deployed image identity or production HTTPS.

## Earlier real-owner observation

The pinned Edge93 standalone wheel exposed this defect after a real owner-completed Home Assistant
sign-in and documented offline restoration. Four checkpoint operations stayed current; the later
creation was retained as one historical operation. The original completed task kept its ID,
revision3 and performed timestamp. Recovery returned the same original later operation without
recreating its task. A normal refresh cleared the misleading warning.

Independent preparation inspection, stale-source refusal, actual activation, same-ID status/resume,
the genuine source rollback checkpoint and normal final shutdown were verified. The selected
database, original flat source and installation metadata hashes were unchanged across shutdown.
This is bounded pre-fix owner evidence, not installed acceptance of this correction.

Exact-head CI, actual images for both CPU families, installed correction acceptance and destination
verification remain separate gates. Full M1/M5, interrupted activation deployment acceptance,
Stable and distribution remain outside this increment's completion claim.
